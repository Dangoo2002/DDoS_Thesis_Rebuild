# Hybrid Machine Learning-Based Real-Time DDoS Detection and Mitigation for Web Applications

## Repository Overview

This repository contains the reproducibility-focused experimental implementation and retained scientific evidence for the thesis:

**Hybrid Machine Learning-Based Real-Time DDoS Detection and Mitigation for Web Applications**

The project investigates machine-learning-based detection of DDoS and related network traffic and extends the offline classification work into a controlled Docker laboratory in which a deployment-compatible detector performs live feature extraction, frozen-model inference, and application-level mitigation.

The repository is evidence-oriented. Experimental inputs, preprocessing artifacts, configurations, trained models, predictions, metrics, controlled traffic records, PCAP captures, runtime measurements, mitigation records, final tables, and final figures are retained so that reported results can be traced back to their experimental sources.

The experimental programme is divided into eleven experiments.

Experiments 001–009 establish the selected CICIoT2023 Dataset A pipeline, classical and neural models, attack-family analysis, runtime benchmarking, a controlled HTTP baseline, an offline mitigation-policy evaluation, and the Hybrid CNN-LSTM evaluation.

Experiment 010 introduces Dataset B, a separate controlled-laboratory dataset derived from captured Docker testbed traffic. It establishes a deployment-compatible 20-feature representation, evaluates candidate window and model configurations using validation data, freezes the selected deployment system, and evaluates it once on held-out test runs.

Experiment 011 uses the frozen Experiment 010 deployment system in an end-to-end controlled laboratory. It performs live packet capture, feature extraction, model inference, detector decision generation, and application-level HTTP mitigation.

The repository intentionally preserves weak, interrupted, imbalanced, or otherwise imperfect experimental results. Results are not replaced with synthetic or manually improved values.

## Scientific Scope

The repository contains two distinct datasets and experimental contexts.

### Dataset A — Selected CICIoT2023 Feature Dataset

Dataset A is a selected subset of the CICIoT2023 CSV feature distribution.

The retained source data are located at:

    data/raw/CICIoT2023_Selected/

The selected subset contains 46 CSV feature files, 39 feature columns, and 10,713,192 observations.

The retained source folders are:

- Benign_Final
- DDoS-HTTP_Flood
- DDoS-SlowLoris
- DDoS-SYN_Flood
- DDoS-UDP_Flood
- Recon-PortScan
- SqlInjection
- XSS

Files with names containing `.pcap.csv` are CSV feature representations derived from packet captures. Experiments 001–009 do not claim to process those files as raw PCAP packet captures.

The source traffic is mapped into four model categories:

- Benign
- DDoS
- Recon
- Web

Dataset A supports Experiments 001–009.

### Dataset B — Controlled-Laboratory Deployment Dataset

Dataset B was created separately during Experiment 010 from controlled benign and high-rate HTTP traffic generated inside the Docker testbed.

Unlike Dataset A, Dataset B is derived from retained packet captures generated by the project's own controlled laboratory.

Dataset B contains two classes:

- Benign
- Attack

The Dataset B feature representation contains 20 deployment-compatible network features:

- packet_count
- duration_seconds
- header_length_mean
- ttl_mean
- fin_fraction
- syn_fraction
- rst_fraction
- psh_fraction
- ack_fraction
- packet_length_sum
- packet_length_min
- packet_length_max
- packet_length_mean
- packet_length_std
- packet_length_variance
- iat_mean
- iat_min
- iat_max
- iat_std
- packet_rate

Feature windows are non-overlapping and are formed within individual experimental runs. Windows do not cross run boundaries.

Candidate packet-window sizes of 10 and 100 packets were evaluated during model development. The final selected deployment system uses 100-packet windows.

Dataset B is not represented as statistically equivalent to CICIoT2023 Dataset A. It is a separate controlled-laboratory dataset created to support deployment-compatible detection experiments.

## Dataset A Partitioning

Experiment 001 performs deterministic file-aware row-level partitioning using seed:

    20261002

The retained Dataset A partition sizes are:

| Partition | Rows |
|---|---:|
| Training | 7,702,608 |
| Validation | 1,236,682 |
| Testing | 1,773,902 |
| Total | 10,713,192 |

Whole-file allocation is preferred where possible. Deterministic row-level partitioning is used where necessary to satisfy the retained partition totals and category representation.

This is therefore not described as a purely file-level split.

The repository also does not claim that the Dataset A split is a chronological or temporal split.

Dataset manifests retain source-file provenance and local SHA-256 values. Those hashes identify the locally retained source files and are not represented as official CICIoT2023 checksums.

## Dataset A Preprocessing

Experiment 002 performs preprocessing using the partitions established by Experiment 001.

The retained pipeline:

1. reads the 39 selected feature columns;
2. replaces positive and negative infinity with missing values;
3. replaces resulting missing values with zero;
4. fits a `StandardScaler` using the training partition only; and
5. applies the fitted scaler to the training, validation, and test partitions.

The validation and test partitions are not used to fit the scaler.

Processed Dataset A artifacts are retained under:

    runs/experiment_002_preprocessing/

Original attack-family provenance is retained separately for later attack-family evaluation.

### Experiment 009 — Hybrid CNN-LSTM

Directory:

    runs/experiment_009_hybrid_cnn_lstm/

Primary scripts:

    scripts/09_train_hybrid_cnn_lstm.py
    scripts/09_evaluate_hybrid_cnn_lstm.py

Experiment 009 evaluates the retained Hybrid CNN-LSTM classifier on Dataset A.

The model consumes input with shape:

    (39, 1)

The architecture contains:

    Conv1D
    -> BatchNormalization
    -> MaxPooling1D
    -> Conv1D
    -> BatchNormalization
    -> MaxPooling1D
    -> LSTM
    -> Dense
    -> Dropout
    -> Softmax

The 39 positions represent the ordered feature axis.

The released Dataset A CSV representation does not retain an explicit timestamp suitable for establishing verified chronological sequences of consecutive observations. The LSTM is therefore interpreted as modelling dependencies across convolutionally transformed feature positions rather than as evidence of validated temporal packet-sequence learning.

Training was interrupted during epoch 8.

Seven complete epochs are retained in the recovered training-history artifact. The recovered history is derived from retained terminal evidence and is not represented as a pristine automatically persisted training log.

The retained held-out test evaluation reports approximately:

- accuracy: 0.895085
- macro F1: 0.289811
- weighted F1: 0.889587

Class-level performance is highly imbalanced. In particular, retained evaluation shows zero Benign recall.

Overall accuracy must therefore not be interpreted as balanced four-class performance.

### Experiment 010 — Deployment-Compatible Dataset B Detection

Directory:

    runs/experiment_010_realtime_detection_mitigation/

Primary scripts:

    scripts/10_init_acquisition_run.sh
    scripts/10_load_acquisition_run.sh
    scripts/10_extract_dataset_b_features.py
    scripts/10_train_select_deployment_model.py
    scripts/10_evaluate_final_test.py

Docker configuration:

    testbed/docker-compose-exp010.yml

Experiment 010 bridges the gap between the offline Dataset A feature representation and a feature representation that can be extracted directly from controlled packet captures.

Controlled benign and high-rate HTTP workloads are generated against a Dockerized victim application. Traffic is captured as PCAP and transformed into the 20-feature Dataset B representation.

Feature extraction is label-blind with respect to the packet-window calculations.

Two non-overlapping packet-window regimes were evaluated:

- 10 packets
- 100 packets

Windows are created independently within each run. Tail packets that do not complete a window are discarded.

The experiment uses run-level separation between model-development partitions. Traffic windows from a run are not treated as independent experimental runs.

Candidate model development evaluates Logistic Regression, Random Forest, and the retained hybrid candidate using validation data.

The final selected deployment system is:

    Logistic Regression
    window size = 100 packets
    decision threshold = 0.5

The scaler is fitted using training data only.

The selected system is frozen before final held-out testing.

The final held-out Dataset B evaluation uses benign B07/B08 and attack A07/A08 runs and contains 480 windows in total:

- 240 Benign
- 240 Attack

The pooled held-out confusion matrix is:

    [[240, 0],
     [0, 240]]

The retained pooled held-out accuracy, precision, recall, F1, balanced accuracy, and ROC AUC are all 1.0 where defined by the retained evaluation.

This perfect controlled-laboratory result must not be interpreted as evidence of equivalent performance on arbitrary Internet traffic, production DDoS attacks, or CICIoT2023 Dataset A.

Dataset B is intentionally treated as a separate experimental distribution.

### Experiment 011 — Live Detection and Application-Level Mitigation

Directory:

    runs/experiment_011_live_detection_mitigation/

Primary scripts:

    scripts/11_live_feature_pipeline.py
    scripts/11_frozen_model_inference.py
    scripts/11_initialize_mitigation_state.py
    scripts/11_live_detector_controller.py
    scripts/11_evaluate_detection_runtime.py
    scripts/11_evaluate_mitigation_service.py
    scripts/11_forensic_reconciliation.py

Docker configuration:

    testbed/docker-compose-exp011.yml

Experiment 011 evaluates the frozen Experiment 010 deployment system in a controlled end-to-end Docker laboratory.

The experiment establishes:

    controlled HTTP workload
        -> packet capture
        -> 20-feature live extraction
        -> frozen scaler
        -> frozen Logistic Regression model
        -> detector decision
        -> shared mitigation state
        -> application-level HTTP enforcement
        -> retained detector/client/victim evidence

The Experiment 011 protocol, feature pipeline, inference implementation, and mitigation implementation were frozen before the final result runs.

Nine final result runs are retained:

- B01–B03: benign traffic, detector enabled, mitigation enabled
- A01–A03: attack traffic, detector enabled, mitigation disabled
- M01–M03: attack traffic, detector enabled, mitigation enabled

Each result run contains 1,000 HTTP requests.

The experimental unit is the run. Packet windows are nested observations within runs and are not represented as independent experimental replicates.

#### Live detection results

The pooled Experiment 011 detection evaluation contains 1,080 windows:

- 360 benign windows
- 720 attack windows

The pooled confusion matrix is:

    [[360, 0],
     [0, 720]]

The retained pooled detection metrics are 1.0.

Single-class per-run or per-condition metrics are interpreted carefully. Balanced accuracy is undefined where only one true class is present. Fixed-label binary macro F1 for those single-class conditions is 0.5 under the retained evaluation convention.

#### Live detector timing

Mean retained feature-to-inference timing is approximately:

| Condition | Mean feature-to-inference time |
|---|---:|
| Benign | 0.002629 s |
| Attack, mitigation disabled | 0.001955 s |
| Attack, mitigation enabled | 0.001967 s |

For mitigation-enabled attack runs, the mean decision-to-enforcement transition is approximately:

    0.002484 s

These are detector-pipeline timing measurements.

They are not HTTP request response times and are not complete external end-to-end network latency measurements.

#### Application-level mitigation

Experiment 011 implements real application-level enforcement.

When mitigation is active, the victim application returns:

    HTTP 429 Too Many Requests

The retained mitigation runs produced:

| Run | HTTP 200 | HTTP 429 |
|---|---:|---:|
| M01 | 108 | 892 |
| M02 | 135 | 865 |
| M03 | 138 | 862 |

Across the three mitigation runs:

- 381 requests received HTTP 200;
- 2,619 requests received HTTP 429;
- all 3,000 transport attempts completed; and
- all 2,619 post-enforcement requests were HTTP 429.

This is genuine controlled application-level enforcement.

It is not:

- iptables blocking;
- firewall rule insertion;
- source-IP blacklisting;
- packet dropping at a network firewall;
- volumetric upstream DDoS scrubbing; or
- evidence of production-scale deployment.

The repository therefore describes Experiment 011 as controlled-laboratory live detection and application-level mitigation.

#### Service measurement limitation

Exact process-level wall-clock duration was not retained for the final Experiment 011 service evaluation.

The retained service analysis therefore uses archived request-span measurements.

These values must be described as request spans and not as process wall-clock runtime.

The limitation is preserved explicitly rather than reconstructing unavailable measurements.

## Relationship Between Experiments 008, 010, and 011

The three experiments represent different stages and must not be conflated.

Experiment 008 evaluates an offline policy over Dataset A predictions. It does not enforce mitigation.

Experiment 010 creates Dataset B, establishes a deployment-compatible feature contract, selects a model using validation data, freezes the selected system, and evaluates it on held-out Dataset B runs.

Experiment 011 deploys that frozen Experiment 010 system into the controlled Docker laboratory and evaluates actual live detection and application-level HTTP 429 enforcement.

Experiment 011 does not retroactively turn Experiment 008 into a live mitigation experiment.

## Reproducibility Model

The repository distinguishes between artifact verification and experimental re-execution.

### Artifact verification

Artifact verification is the preferred method for checking the numerical results reported in the thesis.

Relevant retained evidence includes:

- source-data manifests;
- deterministic Dataset A split metadata;
- processed Dataset A files;
- fitted scalers;
- saved models;
- model configurations;
- predictions;
- confusion matrices;
- metrics;
- attack-family provenance;
- runtime measurements;
- controlled HTTP records;
- Dataset B PCAP captures;
- Dataset B extracted features;
- Dataset B partition metadata;
- selected-system freeze artifacts;
- Experiment 011 protocol files;
- live detector events;
- client ground truth;
- victim access logs;
- mitigation state;
- service evaluation artifacts;
- SHA-256 manifests;
- final tables; and
- final figures.

Historical artifacts should be inspected in place rather than overwritten.

### Pipeline re-execution

The repository contains scripts required to reproduce or inspect the experimental methodology.

However, running scripts that write to existing experiment directories can alter retained evidence.

When independent re-execution is required, use a copy of the repository or otherwise preserve the frozen historical artifact directories first.

Historical model training is not promised to reproduce byte-for-byte across different operating systems, hardware, library builds, threading implementations, or numerical backends.

Experiments 004 and 009 in particular preserve interrupted historical training outcomes.

## Integrity and Hash Manifests

Multiple frozen experiment stages contain SHA-256 manifests.

These manifests provide integrity evidence for the retained artifacts.

A checksum manifest verifies the files and hashes it actually enumerates. It should not be interpreted as proving properties outside its defined artifact set.

Historical manifests are part of the retained scientific record and should not be silently rewritten merely to make an old artifact appear different from what was originally frozen.

## Interpretation Limits

The repository supports the experimental conclusions only within the scope actually tested.

The repository does not establish that:

- Dataset A contains every CICIoT2023 attack type;
- Dataset A `.pcap.csv` files are raw PCAP files;
- Dataset A's 39 feature positions are chronological packet timesteps;
- Experiment 004 is a CNN-LSTM;
- Experiment 009 establishes temporal packet-sequence learning;
- Experiment 009 has balanced high four-class performance;
- Experiment 006 measures HTTP request latency or GPU latency;
- Experiment 007 is a DDoS detection or mitigation experiment;
- Experiment 008 performs live blocking;
- Dataset B is distributionally equivalent to Dataset A;
- Dataset B held-out performance generalizes automatically to arbitrary real-world traffic;
- Experiment 011 performs iptables or firewall enforcement;
- Experiment 011 blocks remote source IP addresses;
- HTTP 429 application enforcement is equivalent to upstream network-layer DDoS filtering;
- the retained laboratory traffic represents Internet-scale volumetric DDoS;
- the system has been validated as a production intrusion-prevention appliance; or
- controlled-laboratory performance establishes production deployment performance.

## Meaning of “Real-Time” in the Final Experiment

Experiment 011 contains a live detector loop operating on traffic generated during the controlled experiment.

It performs packet acquisition, feature extraction, frozen-model inference, decision generation, and application-level enforcement during the running testbed.

The term “real-time” in the thesis context therefore refers to this live controlled-laboratory processing path.

It does not mean that deterministic hard real-time deadlines, carrier-grade throughput, Internet-scale volumetric attack resistance, or production deployment guarantees were established.

---

## Meaning of “Mitigation”

Two different mitigation concepts occur in the repository.

Experiment 008 uses offline mitigation-selection labels over stored predictions.

Experiment 011 implements actual application-level enforcement by causing the victim application to return HTTP 429 responses after the detector activates mitigation.

The final implementation is therefore correctly described as application-level HTTP mitigation.

It must not be described as firewall or iptables blocking.

---

## Experimental Unit and Statistical Interpretation

For Dataset B and Experiment 011, the experimental unit is the controlled run.

Feature windows are observations nested within runs.

A large number of windows must not be interpreted as an equally large number of independent experimental replications.

Per-run and pooled window-level metrics are retained for detector evaluation, while conclusions about repeated experimental behavior must respect the run structure.

## Final Evidence Chain

The project follows the traceability principle:

    experimental input
        -> preprocessing or feature extraction
        -> partition/protocol
        -> experiment configuration
        -> trained or frozen model
        -> predictions/decisions
        -> evaluation metrics
        -> final tables and figures
        -> thesis claims

For Dataset A this begins with the selected CICIoT2023 feature CSV files.

For Dataset B it begins with controlled run acquisition and retained packet captures.

For Experiment 011 it additionally includes the frozen deployment model, live feature pipeline, detector events, mitigation state, client ground truth, victim logs, and service evaluation.

Where evidence is incomplete, the limitation is documented rather than replaced with synthetic measurements.

## Final Scientific Status

The retained experiment record supports the following qualified interpretation:

- Experiments 001–003 establish the selected Dataset A pipeline and classical baselines.
- Experiment 004 is a retained incomplete CNN-Dense validation experiment.
- Experiment 005 provides attack-family-level analysis of Dataset A test predictions.
- Experiment 006 provides CPU batch inference runtime measurements.
- Experiment 007 provides a controlled HTTP service baseline.
- Experiment 008 provides an offline mitigation-policy analysis.
- Experiment 009 provides the retained non-temporal feature-axis Hybrid CNN-LSTM evaluation.
- Experiment 010 establishes a separate deployment-compatible controlled Dataset B and frozen selected detector.
- Experiment 011 establishes live controlled-laboratory detection and actual application-level HTTP mitigation using that frozen detector.

These results support a reproducible controlled-laboratory demonstration.

They do not constitute evidence of production-scale Internet DDoS mitigation.
